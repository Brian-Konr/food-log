# food-log v1.1.4-deletefix 規格

## 問題
10/12 那筆「統一陽光 無加糖超優蛋白豆漿」一開始就沒存進後端（append 失敗，留在 outbox/failed）。之後使用者刪除它，前端排了一個 `softDelete` 到後端，後端找不到該 id 回 `not_found`，前端把它當失敗、還原紀錄並 toast「刪除失敗，已還原 …」。這個失敗 op 留在 IndexedDB，每次打開 app 重試、再失敗、再 toast。

## 修正（路徑皆在 `app/` 下）

### 1. 刪除從未同步的紀錄只在本機處理（`src/api/index.ts` `remove`、`src/App.tsx` `dropOrReverse`）
- `api.remove(table, id)`：若該 id 的 create（`append`／`upsert*`）仍在 outbox 排隊中或在 failed 清單，直接在本機丟掉該 create 與該 id 相關的 op，**不呼叫後端**。
- 決策：從未同步的紀錄刪除時，「已刪除」toast 仍提供「復原」；復原會把它放回原本的狀態（原本在 outbox 就回 outbox，原本在 failed 就回 failed）。
- `dropOrReverse` 除了 outbox 也要檢查 failed 清單。

### 2. 後端 softDelete 冪等（`gas/Code.gs` `softDelete_`、`src/api/mock.ts`）
- id 不存在或已刪除 → 回 `ok`（不再回 not_found 錯誤）。mock 行為一致。
- 前端收到 softDelete 的 `not_found` 也視為成功（相容舊後端）。
- kyujin 權限檢查不變。

### 3. 失敗 toast 只顯示一次（`src/api/index.ts`、`src/App.tsx`）
- `failedNotified`（已通知過的 failed op id）存到 kv（IndexedDB），重開 app 不再重複 toast 同一筆。
- 永久性失敗（如 bad_record、not_found 以外的 4xx 類）toast 提供「放棄」，按下即丟掉該 failed op（及必要時還原本機狀態）。

### 4. 開啟時自動修復（ready 時執行一次）
- 丟掉結果為 `not_found` 的 failed `softDelete`。
- 同一 id 同時有 `append`（未同步/失敗）與 `softDelete` 的配對 → 兩者都丟掉。
- `console.info` 記錄修復數量；**不顯示 toast**。

## 測試
- Unit：remove 未同步 create 不打後端；復原回到原 outbox/failed 狀態；dropOrReverse 檢查 failed；softDelete 對不存在/已刪 id 回 ok（mock + gas 邏輯）；前端 not_found 視為成功；failedNotified 持久化；放棄按鈕；auto-heal 兩種情況與計數。
- E2E（`e2e/real-click.mjs`）：
  - mock 讓 append 回 bad_record → 刪除該筆 → 重新載入 2 次都沒有失敗 toast。
  - 預先在 IndexedDB 放一個舊的 failed softDelete（not_found）→ 載入後被修復、無 toast、紀錄不回來。
- 先跑 `npm run build:gas` 再 `npm test`，然後 `npm run build`。
