1 · Overview

全貌：三個地方、一條主線

手機上的 PWA 永遠先寫本機（所以離線也能記、點下去立刻出現），背景再把「有名字的動作」送到 Cloudflare Worker；Worker 用同一份規則在 D1 定案，再把結果發回每支手機。登入、Kyujin、每日備份都掛在同一個 Worker 上。

iPhone PWA（apps/food-log）

  • React 19 + TanStack Router（#today 等 hash 網址）
  • 資料一律讀本機 Dexie，不等網路
  • sync-client 負責送出、拉回、合併
  • Service Worker 快取整個 App，可離線開啟

Cloudflare Worker（workers/api）

  • Hono 路由：/api/auth/*、/sync/*、/bot/v1/*
  • Better Auth：passkey、一次性登入碼、session
  • 部署時也一起提供前端靜態檔（同一個網址）

Storage

  • D1（SQLite）：你的飲食資料 + 同步記帳 + 登入資料
  • R2：每天 04:00 台北時間的完整匯出

2 · Frontend

前端 PWA：從手指到磁碟的六層

上層只管畫面與「使用者想做什麼」；中間的 sync-client 把每個動作變成本機寫入 + 待送佇列；最底下是手機的 IndexedDB。

打開 App（Root boot）

  1. 這支手機選過「先在這支手機試用」→ 試用模式：開 food-log-local 資料庫，不連 Worker。
  2. 否則用一個很小的 fetch('/api/auth/get-session') 問有沒有登入（登入套件改成要用時才載入）。
  3. 有 session → 打開 food-log-<userId>，開始同步。
  4. 連不上伺服器、但這支手機登入過 → 直接用本機資料打開（離線照常記）。
  5. 確定沒登入 → 登入畫面（passkey／登入碼）。
  6. 之後同步收到 401 → 蓋一層登入畫面，待送資料保留，登入完繼續送。

記一筆（例：點一個品項）

  1. 畫面呼叫 actions.recordLog()：算好份量與營養素。
  2. 變成一個有名字的 mutation：logs.add@1（若同時補填營養素，品項也包在同一個 mutation）。
  3. sync-client 在一個 Dexie 交易裡用 core 的同一份規則執行：檢查、寫畫面表、放進 pending。
  4. 畫面的 live query 立刻看到新列（不等網路）；違反規則（例如店名重複）當場報錯。
  5. 回傳 undo：一律是反向 mutation（logs.delete），不去刪佇列。

3 · Sign-in & session

登入驗證：登入碼開門、passkey 常用、cookie 走天下

沒有註冊頁（disableSignUp），帳號由你在電腦上建立；只有 ALLOWED_EMAILS 裡的人能登入。第一次用登入碼，進來後註冊 passkey，之後都用 Face ID。

第一次登入

  1. 你在 Mac 跑 bootstrap-owner.ts 建立帳號（一次）。
  2. 跑 login-code.ts：產生 XXXX-XXXX-XXXX，D1 只存 SHA-256 hash，15 分鐘、只能用一次。
  3. 手機輸入登入碼 → /api/auth/login-code/redeem → 核銷並檢查允許清單 → 發 session cookie。
  4. 登入狀態下「新增 passkey」：Face ID 建立，綁定網域 food-log.brian-konr.workers.dev。

之後每一次

  1. passkey 登入：拿 challenge → Face ID 簽名 → Better Auth 驗證 → cookie。
  2. Cookie：HttpOnly; Secure; SameSite=Lax，90 天、使用中自動延長。
  3. 每個 /sync/* 請求帶 cookie；Worker 先看 5 分鐘的簽章快取，過期才查 D1。
  4. 沒有有效 session → 401 → App 蓋登入畫面，資料不丟。

Kyujin（bot）

  1. bot-key.ts 發一把 flk_… API key，D1 只存 hash。
  2. 請求帶 Authorization: Bearer；每次都重新確認 key 的擁有者仍在允許清單。
  3. 權限只有 foodlog:read 與 foodlog:write.kyujin：只能改自己記的東西。

4 · Sync

同步：一次循環 = push 再 pull

核心保證：每個動作在伺服器剛好生效一次（重送也一樣），而且每支手機最後看到的都和伺服器一致。觸發時機：打開 App、回到前景、恢復網路、每次記錄後、前景時每 60 秒。

Push（送出）

  1. 從 pending 取最多 10 筆，POST /sync/push，帶 clientId 與 X-FoodLog-Client 版本。
  2. 伺服器對每筆：mutationId 已處理過 → 直接回當時存下的結果（所以重送不會重複）。
  3. 否則讀資料 → 跑同一份 mutator → 用一個原子 batch 寫入：版本號比對（CAS）、版本 +1、資料列、這支手機的游標。
  4. 版本號被別人搶先 → 重試（最多 5 次）；業務錯誤 → 記下結果並推進游標。

Pull + Rebase（拉回、合併）

  1. GET /sync/pull?cookie=<epoch>:<version>：拿版本號比 cookie 新的列，每頁 1,000 列。
  2. epoch 不同（例如從備份還原過）→ reset:true，整份重抓。
  3. 收到的列寫進 srv_*；已確認的 pending 移除，失敗的移到 failed。
  4. 畫面表 = 伺服器狀態 + 重播還沒確認的 pending（不變式，有 property test 守）。

出錯時

  1. 斷網或 5xx：等 2、5、15 秒各重試一次，之後等下一個觸發時機。
  2. 401：停下、蓋登入畫面，pending 保留。
  3. 409 client_too_old：顯示「有新版本，請重新載入」。
  4. 業務錯誤：進設定頁的失敗清單，可以重試或捨棄。

5 · Data

資料：兩個資料庫，各有分工

手機上的 Dexie 是「伺服器確認過的副本 + 還沒送出的動作」；D1 是唯一正本。所有業務表都以 (user_id, id) 為主鍵、STRICT 型別、軟刪除（deleted_at），每列帶 version 讓 pull 知道從哪裡接著拿。

D1 · 三組表

  • Business：stores、items、logs、weights、favorites、config（你的資料）。
  • Sync：meta（目前版本號與 epoch）、cas_guard、sync_clients（每支手機處理到哪）、mutation_outcomes（每筆的結果，供重送查詢）。
  • Auth：Better Auth 的 user、session、account、passkey、apikey、verification，加上 login_codes。

每日備份

  1. Cron 每天 20:00 UTC（台北 04:00）開始，分段匯出每張表成 JSON + logs.csv。
  2. 做不完由每 5 分鐘的第二個 cron 接著做（免費方案每次 CPU 很短）。
  3. 全部寫完才寫 _ok.json；匯出期間資料有變 → consistent:false。
  4. restore-drill 在本機還原比對；D1 遺失時可產生 SQL 寫回，並換新 epoch。

從舊系統搬過來

  1. fetch-sheet 唯讀抓整份 Google Sheet。
  2. transform 修正不合規則的列，全部記在 anomalies。
  3. emit-sql --reset → 套用 → verify 逐表比對。
  4. 回滾用 reverse-export 把切換後的新資料寫回 Sheet。

6 · Worker routes

Worker 路由表

一個 Worker、一個網址。下面是它對外的每一個入口。

入口誰在用驗證方式做什麼
/api/auth/*PWA—（這裡就是登入）passkey 登入／註冊、登入碼兌換、登出、取得 session
POST /sync/pushPWAsession cookie送最多 10 個 mutation，回每筆結果
GET /sync/pullPWAsession cookie依 cookie 回新變更（每頁 1,000 列）與本機的錯誤
/bot/v1/*KyujinBearer API keyread、summary、trends、history、mutate（7 種動作）、openapi.json
/telemetryPWA限流只收錯誤碼與版本，1 KB 上限
/api/health你—健康檢查，含 authPrewarm 狀態
cron 0 20 * * *、*/5 20 * * *Cloudflare—每日匯出到 R2（可續跑）
其他路徑瀏覽器—前端靜態檔（deploy:with-app 時），SPA fallback
