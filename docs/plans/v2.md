## 0. 對 PRD 的修正（已定案，寫回 PRD）

1. **D1 沒有互動式交易。** Worker 不能 `BEGIN` → 讀 → 跑 JS → `COMMIT`，只有 `db.batch([...])` 是原子的。所以 mutator 的做法改成樂觀並行控制：
   - 先讀資料，寫入只放進緩衝區。
   - 最後用一個 batch 提交。batch 的第一句是對 `meta.version` 的比對保護（CAS guard）：
     ```sql
     INSERT INTO cas_guard(ok) SELECT CASE WHEN value=?v THEN 1 ELSE 0 END FROM meta WHERE key='version'; -- ok CHECK(=1)
     DELETE FROM cas_guard; UPDATE meta SET value=?v+1 WHERE key='version'; …寫入列 version=?v+1…
     ```
   - 比對失敗就重試，最多 5 次，之後當成暫時性錯誤。
   - 部分唯一索引在資料庫層再擋一次。
   - spike 若證明不可行，退路是 SQLite-backed Durable Object（要改 PRD）。
2. **Workers 免費方案每個請求只有 10 ms CPU。**
   - `cookie=0` 的全量 pull 一開始就分頁，每頁約 1,000 列（`PULL_PAGE_ROWS`；原為 2,000，見下方真機實測），只在版本號之間切。
   - 匯入每個版本最多寫 500 列。
   - Cron 匯出依表分段。
   - 階段 0 實測 CPU 時間。
   - **（2026-10-15 真機實測）** 部署到 `food-log-spike.brian-konr.workers.dev`、用 iPhone 主畫面 PWA 加 `wrangler tail` 量到的數字（細節見 [`v2-spike.md`](v2-spike.md) 第 7 節）：
     - 熱請求 0–1 ms CPU；`/api/health`（不建 Better Auth）冷 2–4 ms。
     - **每個新 isolate 第一次建立 Better Auth 要 18–33 ms CPU**（免費方案上限 10 ms）；passkey `verify-authentication` 23 ms、`generate-options` 9 ms。
     - pull 一頁 2,000 列 6–10 ms CPU（貼著上限）；wall time 約 420–940 ms，因為 4 次 D1 讀取依序來回。
     - **決定**：(a) `betterAuth()` 移到模組（global）scope，用 `import { env } from "cloudflare:workers"` 在載入時建好唯一的實例，算 Worker 啟動時間、不算請求 CPU；(b) pull 的 cursor／錯誤／meta／列讀取合併成最多兩個 D1 往返（閒置輪詢一個）；(c) 每頁降到 1,000 列。這三項做完仍超過才升級 $5 方案。
3. **Better Auth 的 passkey 只能在已登入時註冊。** 一次性登入碼同時負責第一次登入和 passkey 丟失時的備援：
   - 15 分鐘有效、只能用一次
   - D1 只存 SHA-256 hash
4. **`favorites`、`config` 也要有 `version`／`deleted_at`。** 否則 pull 帶不走「取消收藏」。
5. **`pnpm deploy` 是 pnpm 內建指令。** 驗收 #19 改成 `pnpm run deploy`。
6. **passkey 的 RP ID 是完整的 worker 主機名。** `workers.dev` 在 Public Suffix List 上，所以 RP ID 不能用上層網域。**（2026-10-15）** 正式 v2 的主機是 `food-log.brian-konr.workers.dev`（workers.dev 子網域 `brian-konr`），RP ID 就是這個主機名，`APP_ORIGIN` 設 `https://food-log.brian-konr.workers.dev`（`workers_dev: true`、`preview_urls: false`）。
7. 其他：
   - R2 免費方案可能要求綁卡，進階段 1.4 前確認。
   - `@cloudflare/vitest-pool-workers` 可能需要和 vitest 5 不同的版本，`workers/api` 可以鎖自己的版本。（2026-10-15：pool 已棄用，`workers/api` 改用 `@cloudflare/vitest-plugin` 1.4.3，它支援 vitest 5，所以和其他套件同一個 vitest 5.0.5。）
8. **（2026-10-15 spike 修正）** 階段 0 實作後對計畫的修改（細節見 [`v2-spike.md`](v2-spike.md) 第 5 節）：
   - **`MAX_PUSH` 改 10**：免費方案每次呼叫最多 50 次 D1 查詢，一筆 mutation 約 4 次。若 D1 把 batch 內每條語句都算一次，連 10 筆也太多（要降到 4–5），部署後驗證。
   - **D1 的 `GLOB`／`LIKE` 樣式上限 50 bytes**：`ts GLOB '…'` 建表就失敗。格式檢查改用 `date()`／`strftime()`，而且要補 `IS NOT NULL`（`CHECK` 遇到 NULL 會通過）。
   - **CAS 有第二個 guard**：除了 `meta.version`，還要比對 `sync_clients.last_mutation_id`，否則錯誤／ignored 路徑（版本號不變）擋不住並行重複處理。只有 guard 失敗才是衝突；唯一索引擋下寫入且版本與 cursor 都沒變時是確定性錯誤，記為 `bad_record`，不重試（否則永遠 503）。
   - **重送回傳原本的結果**：`mutation_errors` 改為 `mutation_outcomes`（`ok`＋`result`／錯誤），每次 commit 在同一個 batch 內刪掉早於 `mutationId - 200` 的紀錄。
   - **`weights` 主鍵是 `(user_id, id)`**，兩個使用者可以用同一個 id。
   - **`APP_ORIGIN` 在 localhost 以外必填**：沒設就回 500 `APP_ORIGIN not configured`（fail closed）；auth 實例單一快取，鍵為 `(APP_ORIGIN, ALLOWED_EMAILS, BETTER_AUTH_SECRET 的雜湊)`；**2026-10-15 起 production 的實例在模組載入時就建好**（`src/auth.ts` 的 `prewarm()`，用 `cloudflare:workers` 的 `env`；沒有 `APP_ORIGIN`、沒有 secret 或建構失敗就跳過，請求時才照舊懶建，所以 localhost 開發與 fail closed 不變）。
   - **Better Auth `session.cookieCache`（5 分鐘）**：`/sync/*` 不必每次打 D1；撤銷最多 5 分鐘後生效，過期或無效的 session 仍回 401。
   - **`@cloudflare/vitest-pool-workers` 已棄用**（改名 `@cloudflare/vitest-plugin`，支援 vitest 4／5）：階段 1 建議直接換成 plugin。
9. **（2026-10-15 階段 1 步驟 4，`workers/api` 實作）** D1 實作時又發現的事：
   - **D1 的複合 `SELECT`（`UNION ALL`）最多 5 項**，六張表串不起來（`too many terms in compound SELECT`）。pull 的 `rowsAfter` 改成兩個 batch：先對每張表取第 limit 列的版本號（取最小值當截止版本），再讀各表到截止版本為止的列。
   - **guard 通過後的任何約束失敗**（部分唯一索引、`CHECK`、`NOT NULL`、STRICT 型別）都是確定性錯誤：版本與 cursor 沒變就丟 `bad_record`（不只唯一索引）。
   - **查詢預算**：同一個 `UserStore` 內，前一筆提交成功後，下一筆的 `begin()` 不再讀版本號與 cursor（用剛提交的值，guard 會驗證，猜錯就是衝突、清掉猜測、重讀重試）；`D1Tx` 在一次嘗試內快取讀取。10 筆 `weights.upsert` 的 push 是 32 次 D1 呼叫（原 41），10 筆「新品項＋店家」的 `logs.add`（最重的一種）是 42 次。**batch 在免費方案是算一次還是每條語句都算，仍待部署後驗證**（第 8 點同一個疑問）。
   - **`mutation_outcomes` 的修剪只刪 `ok=1`**：業務錯誤（`ok=0`）不修剪，前端靠它提示（core 契約）。
   - **Bot 沒有裝置計數器**：`/bot/v1/mutate` 用 `bot:<key id>` 當 clientId、cursor+1 當 mutation id；兩個並行請求可能選到同一個 id，第二個會把第一個的結果當成重送。所以 begin 時發現 cursor 不是推導 id 時的值就整個重來（最多 5 次，之後 503）。
   - **Bot 金鑰**：Better Auth `@better-auth/api-key` 1.7.10（獨立套件）；key 存 `base64url(SHA-256(key))`，`permissions` 是 `{"foodlog":["read","write.kyujin"]}`，`metadata.actor` 必須是 `kyujin`；外掛預設每天 10 次的速率限制必須關掉。金鑰由 `scripts/bot-key.ts` 印出的 SQL 寫入（沒有公開的建立端點）。
   - **`@cloudflare/vitest-plugin` 1.4.3 + vitest 5.0.5**（不需要 vitest 4）。

## 1. 分支策略（長期 `v2` 分支）

- 從 `main` 開 `v2`，用 `git worktree add ../food-log-v2 v2` 開發。`main` 的工作目錄留給 v1 熱修。
- **`main`**：只放 v1 的修正。v1 部署方式不變：
  - `cd app && npm ci && ./scripts/deploy-gh-pages.sh`
  - `npm run deploy:gas`
- **`v2`**：
  - 第一個 commit：`git mv app apps/food-log`，再把 `apps/food-log/gas/` 和 `apps/food-log/test/gas-fakes.ts`、`gas-*.test.ts` 移到 `legacy/gas/`、`legacy/test/`。這樣切換前都還能跑舊 `Code.gs` 對照測試。
  - 每個階段結束（以及 `main` 有 v1 修正時）執行 `git merge main`。
  - 合併規則寫進 v2 根目錄的 `AGENTS.md`：
    - `main` 上 `app/gas/**` 的改動 → 對應到 `legacy/gas/**`
    - `app/src/**` 的改動 → 手動移植到 `apps/food-log`；被重寫的檔案以 v2 為準
    - 每次合併都在 commit message 列出移植清單
- **階段 0** 用拋棄式分支 `spike/v2-auth-sync`（從 `main` 開）。證明可行的程式碼再拿到 `v2`。
- **v1 唯讀開關**（3.1）是 v1 的改動，做在 `main`，再合併進 `v2`。
- **CI**：新增 `.github/workflows/ci.yml`。
  - `main` 跑 v1：`cd app && npm ci && npm test && npm run build`。
  - `v2` 跑 `pnpm i --frozen-lockfile && pnpm -r typecheck && pnpm -r test`，加上 `legacy` 對照測試。
  - Playwright 用手動觸發或每晚跑。
- **切換時**：`v2` 合併回 `main`，`main` 從此就是 v2。打 tag `v1-final`，供回滾使用。

## 3. 核心設計

### 3.1 `Tx` 介面（Dexie、D1、記憶體三種實作共用）

```ts
interface Tx {
  get<T extends Table>(t: T, id: string): Promise<Row<T> | undefined>
  liveWeightOnDay(day: string): Promise<WeightRow | undefined>
  liveStoreByNorm(norm: string, exceptId?: string): Promise<StoreRow | undefined>
  itemsOfStore(storeId: string): Promise<ItemRow[]>
  getConfig(): Promise<ConfigRow>
  put<T extends Table>(t: T, row: RowInput<T>): void
}
type Ctx = { actor: { kind: 'owner' | 'bot'; name: 'app' | 'kyujin' }; now: () => number }
```

- **先讀後寫**：mutator 的讀取全部放在第一個 `put` 之前。`MemoryTx` 在測試裡會擋「寫了之後又讀」，因為 D1 版的緩衝寫入在讀的時候看不到。
- **回傳**：成功時回傳結果，例如 `{ignored:'deleted'}`、`{duplicate:true}`、`{rowId, overwritten, prevKg}`；失敗時丟 `MutationError(code, message, details?)`。

### 3.2 Mutation 目錄（全部 `@1`，參數用 zod 驗證，規則從 `app/gas/Code.gs` 搬過來）

| 名稱 | 重點 |
|---|---|
| `logs.add` | `{log, item?}`：`item` 補填或自建在同一交易裡先寫，**取代 groupId**。快速記錄必須 `qty=1`、`grams` 為 null、`src=其他`、沒有店家。`day==taipeiDay(ts)`、不能是未來日期。重複 id 回 `duplicate`。source 規則照 `resolveLogSource_`。`last_eaten_at` 只往後更新 |
| `logs.update` | 白名單欄位（qty, grams, kcal, protein, fat, carb, ts, day, name）。Bot 先檢查權限 → `not_found` → `ignored:deleted`。不能改 source。用合併後的列重新驗證。**有意的改善（與 Code.gs 不同）**：`name` 寫入時去掉頭尾空白（Code.gs 驗證時 trim、寫入時卻存原字串） |
| `logs.delete` / `logs.restore` | Bot 只能動 `source=kyujin` 的列。**delete 照 v1.1.4**：owner 刪不存在的列回 `{ignored:'missing'}`、已刪除的回 `{ignored:'deleted'}`，都不寫入、不回 `not_found`；Bot 刪的列不存在或不是 kyujin 的 → `forbidden`。restore 不存在仍是 `not_found` |
| `items.upsert` | `fm:`／`711:` → `forbidden`。`ov:` 只有 owner、`kind=補填`、`base_id=id.slice(3)`。`u:` 必須 `kind=自建`；店家品項 `src=其他`，而且店家沒被刪。Bot 規則照矩陣。`created_by` 建立後不變。**`fav` 移除** |
| `items.delete` / `items.restore` | Bot → `forbidden`。delete 不存在／已刪除同 `logs.delete`（`ignored`，不寫入）。**restore 有意與 Code.gs 不同**：品項的店家已刪除或不存在 → `bad_record`（『這家店已經刪除』），要先 `stores.restore` |
| `stores.upsert` | `s:` 前綴、名稱不空白。NFKC `normName` 重複回 `duplicate_name`，附 `{existingId, existingName}`。`created_by` 依 actor。存 `name_norm`。`last_eaten_at` 不是參數 |
| `stores.delete` / `stores.restore` | Bot → `forbidden`。delete 不存在／已刪除同 `logs.delete`。連帶刪除時在品項寫 `cascade_of=storeId`；復原時還原 `cascade_of=storeId` 的品項。取代 v1 用相同 `updated_at` 比對的做法 |
| `weights.upsert` | kg 30–250、最多一位小數。重複 id 回 `duplicate`。當天已有未刪除的列 → 覆寫 kg 和 ts，保留原 id，回 `{overwritten, prevKg}`；否則新增。Bot 可以用 |
| `weights.delete` / `weights.restore` | Bot → `forbidden`。delete 不存在／已刪除同 `logs.delete`。復原時若當天已有一筆，回 `bad_record` |
| `favorites.set` | `{item_id, fav}`，只有 owner。取代 `fav_ids` 和 `items.fav` |
| `config.set` | `{key, value}`，只有 owner。驗證規則照 `setConfig_`，存成有型別的欄位 |

- **Registry**：`name@v → {args, run}`，同時保留目前版和前一版。`CLIENT_VERSION` 是整數。
- **權限**：`permissions.ts` 寫成純函式，用表格式測試覆蓋 PRD §3.1 的每一格，錯誤的判斷順序和 `gas-kyujin.test.ts` 一致。

### 3.3 D1 schema 重點（`migrations/0001_init.sql`，STRICT）

- **共同欄位**：`user_id, version, deleted_at, updated_at`，每張表都有 `(user_id, version)` 索引。
- **約束**：
  - `stores`：`unique(user_id, name_norm) where deleted_at is null`。
  - `items`：用 CHECK 寫出 `ov:`／`u:` 的規則，以及「有店家就必須 `src=其他`」；另有 `cascade_of` 欄。
  - `logs`：`CHECK(day = date(ts,'+8 hours'))`、`ts` 格式（**2026-10-15 spike 修正**：D1 的 `GLOB`／`LIKE` 樣式上限 50 bytes，改用 `date()`／`strftime()` 檢查並加 `IS NOT NULL`）、快速記錄的 CHECK、`logs(user_id, day)` 索引。
  - `weights`：`PRIMARY KEY (user_id, id)`（**2026-10-15 spike 修正**，不是單獨的 `id`）、`unique(user_id, day) where deleted_at is null`、`round(kg,1)=kg`。
  - `favorites`：主鍵 `(user_id, item_id)`。
  - `config`：有型別的欄位，`remind_meal_times` 用 `json_valid`。
- **同步、登入、Better Auth 的表**：`meta`（version、epoch）、`cas_guard`、`sync_clients`、`mutation_outcomes`（**2026-10-15 spike 修正**：原 `mutation_errors`，成功的結果也存）、`login_codes`，以及 Better Auth CLI 產生的表。
- **migration 規則**：
  - 只能做「先加、後刪」（expand → contract）。
  - drizzle-kit 做不出 STRICT 或 CHECK 的部分，就手寫 SQL。
  - 用一個 workers 測試檢查 `sqlite_master`，確認每張表都是 STRICT、部分唯一索引都在。

### 3.4 同步協定

```
POST /sync/push  X-FoodLog-Client: <CLIENT_VERSION>
  { clientId, mutations: [{ id, name: "logs.add@1", args, clientTs }] }   ≤10 筆（D1 免費方案每次呼叫最多 50 個查詢，spike 實測每筆約 4 個；2026-10-15 spike 修正：原為 ≤50）
→ 200 { lastMutationId, results: [{id, ok, result?} | {id, ok:false, error, message, details?}] }
→ 409 { error:'client_too_old', minClientVersion }   401 / 5xx（暫時性，退避 2/5/15s）
GET /sync/pull?cookie=<epoch>:<version>&clientId=…&afterMutationId=…
→ 200 { cookie, more, reset, lastMutationId, minClientVersion,
        changes:{stores,items,logs,weights,favorites,config}, errors:[…本裝置的業務錯誤] }
```

伺服器處理每一筆 mutation（`core/server/process-push.ts`）：

1. `id <= lastMutationId`：已經處理過，直接回傳當時的結果（成功結果存在 `mutation_outcomes`，只保留每台裝置最近 200 筆；更舊的回 `{replayed:true}`；業務錯誤是同一張表的 `ok=0` 列，不修剪。**2026-10-15 spike 修正**：成功的 `result` 也存下來，原本只存錯誤，且那張表叫 `mutation_errors`）。
2. zod 驗證失敗：回 `bad_record`。
3. 讀到目前版本號 V，執行 mutator，用一個 batch 提交：
   - CAS guard：`meta.version` 仍是 V，而且這台裝置的 cursor 仍是先前讀到的值
   - 版本號 +1
   - 寫入資料列
   - 寫入 `mutation_outcomes`（成功結果）、更新 `sync_clients`（**2026-10-15 spike 修正**：條件式 UPDATE 擋不住版本號不變的路徑，所以 cursor 是第二個 CAS guard）
   - guard 通過之後才撞到部分唯一索引（店名、同一天體重）是業務錯誤 `bad_record`，不是暫時性衝突（不重試）。只有版本與 cursor 都沒變才算確定性錯誤；有變就是別人先提交，當成衝突重試
4. 業務錯誤：寫入 `mutation_outcomes`（`ok=0`），並推進 `last_mutation_id`。版本號不變。
5. `ignored` 或 `duplicate`：只推進 `last_mutation_id`。
6. 其他錯誤：中止並回 503。

`ServerStore`（`core/server/store.ts`，契約的唯一來源）只有 `forUser(userId)`，回傳綁定使用者的 `UserStore`；push／pull 只吃 `UserStore`。pull 的讀取順序是 cursor（lastMutationId、錯誤）→ meta → 列，回應才不會宣稱一筆列還沒帶上的 mutation。

**（2026-10-15 真機實測）** 真機上 pull 的 wall time 是 420–940 ms，原因是 D1 往返是循序的（cursor、錯誤、meta、列各一次）。`UserStore` 新增選用方法 `pullSnapshot()`，pull 有它就優先用（沒有就逐一讀取，語意相同）。D1 版：第一個 `db.batch` 一次讀 cursor、錯誤、meta 和六張表的頁邊界探測；第二個 `db.batch` 讀列。一個 batch 是 D1 上的一個原子快照，所以 cursor／錯誤／meta 互相一致，而且「先讀 cursor」的保證仍然成立：cursor 宣稱的 mutation 的列和 cursor 在同一個 batch 提交，一定出現在稍後才讀的列裡。cookie 已經是最新版本（閒置輪詢，最常見）時完全不讀列，只要一個往返；需要 reset 時 pull 再用 `rowsAfter(0)` 讀（罕見）。每頁列數同時從 2,000 降到 1,000（`PULL_PAGE_ROWS`），讓 pull CPU 保持在 10 ms 以下並留有餘裕。

`epoch` 不一致時，pull 回 `reset:true`。從備份還原或最後一次重新匯入時，會寫入新的 `epoch`。

### 3.5 前端（Dexie）與 rebase

**Dexie 資料庫**：`food-log-<userId>`；本機試用模式用 `food-log-local`。

| 表 | 內容 |
|---|---|
| `srv_<table>` | 伺服器最後確認的狀態 |
| `<table>` | 畫面讀的內容：`srv_<table>` 加上重播的待送動作 |
| `pending` | `{mutationId, name, args, touched[]}` |
| `failed` | 業務錯誤，給 UI 重試或捨棄 |
| `meta` | clientId、cookie、lastMutationId 等 |

**`mutate()`**：在一個 Dexie 交易裡，用 `LocalTx` 執行 mutator → 寫進 `pending` → 排程 push。業務錯誤當下就丟出，UI 立刻提示（取代 `App.findDup`）。

**Rebase**（pull 之後，一個 Dexie 交易）：

1. 把收到的變更套進 `srv_*`。
2. 確認或移除已處理的 pending；有錯誤的移到 `failed`。
3. 髒鍵 = 收到的變更 + 所有 pending 的 `touched`。
4. 每個髒鍵：`srv` → view。
5. 依序重播剩下的 pending。

多頁 pull：中間頁（`more=true`）只寫 `srv_*`（reset 時第一頁清 `srv_*`）和 cookie，畫面表不動；收到的鍵累積在 `meta.pullRun`。最後一頁才處理確認、算髒鍵（整輪收到的鍵 ∪ 所有 pending 的 `touched`；reset 再加上舊的 srv／畫面所有鍵），整輪只重播一次。

push 遇到 4xx（非 401／409／408／429）：二分成一筆一筆重送，仍 4xx 的那筆（`failed`、`bad_request`）離開 `pending` 並重建畫面，其餘繼續。

不變式：view == fullRebuild(srv, pending)（多頁 pull 進行中除外），用 property test 驗證。

**觸發時機**：打開 App、回到前景、`online`、每次 mutate 之後、前景時每 60 秒。退避依序等 2、5、15 秒。
- 401 → 進入登入狀態，pending 保留。
- 409 → 顯示「有新版本」。

### 3.6 Undo 與失敗

Undo 一律送一個反向 mutation，不從佇列刪掉原本的那筆，避免和正在進行的 push 衝突。

| 動作 | Mutation | Undo |
|---|---|---|
| 記一筆（可能同時補填） | `logs.add` | `logs.delete`（補填保留） |
| 快速記錄 | `logs.add` | `logs.delete` |
| 收藏 | `favorites.set` | 反向的 `favorites.set` |
| 刪除品項 | `items.delete` | `items.restore` |
| 刪除店家 | `stores.delete` | `stores.restore` |
| 記體重（當天沒有紀錄） | `weights.upsert` | `weights.delete(rowId)` |
| 記體重（覆寫） | `weights.upsert` | `weights.upsert(prevKg, 新 id)` |
| 編輯紀錄 | `logs.update` | `logs.update`（舊值） |
| 刪除紀錄 | `logs.delete` | `logs.restore` |

- 失敗的 UI 沿用 v1 文案，由 `failed` 表產生。
- 重試 = 用新的 mutationId 再 `mutate` 一次。

## 9. 風險

| 風險 | 緩解 |
|---|---|
| D1 沒有互動式交易 | CAS batch + 部分唯一索引，spike 驗證；退路是 DO SQLite |
| 10 ms CPU 限制 | 分頁、分段匯出、階段 0 實測；碰到就升級 $5。**2026-10-15 真機實測**：新 isolate 建 Better Auth 18–33 ms、pull 2,000 列 6–10 ms；已把 Better Auth 移到 global scope（算啟動時間）、pull 讀取合併成最多兩個 D1 batch、每頁降到 1,000 列。這三項做完仍超過才升級 $5 |
| Better Auth API 變動 | 鎖定確切版本 |
| iOS PWA 的 passkey 或 cookie 保存 | 階段 0 關卡；一次性登入碼 |
| `v2` 分支和 `main` 的合併衝突 | v1 原則上凍結；每階段合併一次；移植清單寫在 commit message |
| Dexie 交易在 await 非 Tx 操作時自動提交 | lint 規則 + LocalTx 測試 |
| 飲食資料流進公開 repo | `out/` 進 gitignore + security test；測試資料一律合成 |
| GitHub Pages 的舊 Service Worker | `selfDestroying` 導向版本 |

## 驗證方式（整體）

- **每個階段結束**：`pnpm -r typecheck && pnpm -r test` 全過；`legacy` 對照測試全過；`main` 上 `cd app && npm test && npm run build` 照常通過。
