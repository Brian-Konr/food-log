## 1. Toast 固定 3 秒，跟同步重畫無關

計時語意：

- `id` 變了（新 toast 取代舊的）：剩餘時間重設為這次的 duration（預設 3000），重新倒數。
- 父層重畫、`onGone` 換了一個函式、`id` 沒變：不要清掉正在跑的 timeout，剩餘時間不要歸零。
- 按住（`held === true`）：暫停。暫停時把已經走掉的時間從剩餘時間扣掉。放開後只等**剩下的**毫秒，不要重新等滿 3 秒。
- 剩餘時間到了：呼叫 ref 裡的 `onGone` 一次。

手勢加在 `role="status"` 那一層（不是外層 `pointer-events-none`）。用 `setPointerCapture`，手指滑出元素仍收得到 `pointerup`／`pointercancel`。起點的 `pointerdown` 如果目標在「復原」`<button>` 裡，不要開始這套手勢（按鈕自己的 `onClick` 維持：先 `void t.undo?.()` 再 `gone()`）。

| 事件 | 行為 |
|---|---|
| `pointerdown`（不是復原鈕） | `held = true`，記下 `clientX/clientY/pointerId`，capture |
| `pointerup`，位移 < 10px 且按下不到 300ms | 點一下：呼叫 `onGone`，不要呼叫 `undo` |
| `pointerup`，`dy > 24` 且 `dy > Math.abs(dx)`（往下滑） | 呼叫 `onGone` |
| 其他 `pointerup`（按住後放開、或橫向滑） | `held = false`，用剩餘時間繼續倒數，不要關掉 |
| `pointercancel` | 清起點，`held = false`，繼續倒數。不要關掉，不要把 `held` 留在 true |
| `pointerleave` | 若這個 pointer 沒有 capture 在元素上，同樣繼續倒數。有 capture 時交給 `pointerup`／`pointercancel`，不要在 leave 時提早關掉 |

## 2. 寫入失敗一次不顯示「連不到 Google 試算表」

### 根因

`src/api/index.ts` 的 `flush` 在 `NetworkError` 時立刻 `online = false`（約第 252 行）。`networkState` 在 `pending > 0` 且 `backendOk === false` 時回 `'unreachable'`。`NetworkBanner` 對 `'unreachable'` 和 `'offline'` 都畫「連不到 Google 試算表」。逾時也是 `NetworkError`（`gas.ts` 裡 `kind === 'timeout'`）。Mock 離線丟的是 `new NetworkError()`，`kind` 預設 `'fetch'`。

現在的 `armRetries` 在失敗當下同時排 2s、5s、15s 三個 `setTimeout`。一次嘗試可能要 55 秒，後面的 timer 會撞上同一個 `flushing` promise，被算成一次。規格要的是**依序**三次重試都失敗才出橫幅。

### 重試時序（改 `src/api/index.ts`，取代現在的平行 `armRetries`）

用一個 wave，間隔依序是 **2000、5000、15000**。上一個 `flush` 結束才排下一個。不要在失敗當下把三個 timer 一起排好。

建議狀態：`retryWave`（這波已經排程過幾次，0–3）、`retryTimer`（目前那個 timeout，沒有就是 `null`）。

- `clearRetries()`：清掉 timer，`retryWave = 0`。佇列空了（現有 `if (!outbox.length) clearRetries()`）或某次 `flush` 成功把佇列送完時呼叫。成功時 `online = true`（現有第 250 行留著）。
- `scheduleRetry(isNetwork: boolean)`：
  - `retryTimer != null` 就 return（不要疊兩個 timer）。
  - `retryWave >= 3`：若 `isNetwork && outbox.length > 0`，設 `online = false`。若這次不是 NetworkError（`busy`、`server_error`），**不要**設 `online = false`。然後 return。
  - 否則用 `RETRY_GAPS_MS[retryWave]` 排一個 timeout，先把 `retryWave += 1`，timer 觸發時先把 `retryTimer = null` 再 `void flush()`。
- `flush` 的 `catch`：`err instanceof NetworkError` 時**不要**設 `online = false`。把 `outbox[0]` 標成看過網路失敗（見下），呼叫 `scheduleRetry(true)`，`break`。
- `kind === 'timeout'` 走同一條，不要另開捷徑。逾時表示後端可能已經寫入；重試仍送佇列裡的同一筆（`stripForSend` 會送原本的 `record.id`）。不要丟棄、不要換 id、不要在這一次把使用者判成斷線。
- 暫時性的伺服器錯誤（現有 `!PERMANENT_ERRORS` 那支，含 `busy`）改呼叫 `scheduleRetry(false)`，仍然不要在第一次就 `online = false`。三次用盡後也**不要**因為 busy 把 `online` 設成 false。
- 永久錯誤仍移到 `failed`，不進這個 wave。

三次的定義（測試就照這個時間軸）：

1. 第一次 `flush`（`appendLog` 內部那次）失敗：排 2 秒，`online` 仍是 true。
2. 2 秒那次失敗：排 5 秒，`online` 仍是 true。
3. 5 秒那次失敗：排 15 秒，`online` 仍是 true。
4. 15 秒那次還是 `NetworkError`：`online = false`。這時橫幅才可以出現。
5. 任一次成功且佇列空了：`clearRetries()`，`online = true`，後面的間隔不要再跑。

`status().online` 就是 `useFoodLog` 的 `backendOk`。橫幅不另做一套旗標。

### `src/data/network.ts`

```ts
export function networkState(s: {
  browserOnline: boolean
  backendOk: boolean
  pending: number
  failStreak: number
  hasCache: boolean
}): NetworkState
```

規則，依這個順序：

1. `!browserOnline` → `'offline'`（橫幅，就算有快取也顯示）。
2. `!backendOk && pending > 0` → `'unreachable'`。`backendOk` 只有在寫入重試 wave 用盡時才會是 false，所以佇列裡有東西不再等於「失敗一次就出橫幅」。
3. `hasCache` → `'online'`。有快取的讀取失敗不出橫幅（`failStreak >= 2` 也不出）。頂列交給現有的 `SyncBadge`：`error-cached` 已經是「沒有同步 · 重試」，`cached-syncing` 已經是「同步中」。不要改 `SyncBadge` 的文案。
4. `failStreak >= 2` → `'unreachable'`。沒快取的讀取，含連續兩次逾時（逾時不會把 `online` 設成 false，所以這條不能只看 `backendOk`）。
5. 其他 → `'online'`。

`useFoodLog.ts` 呼叫處加上 `hasCache: cache != null`。

`NetworkBanner.tsx` 不要改字，也不要改「本機試用」那條。

### 規格裡「連續 2 次 NetworkError」怎麼落地（不要猜成另一套）

- **寫入**：連續兩次不夠。橫幅只在 2／5／15 這三次排程都跑完且最後仍是 `NetworkError` 時出現。中間有一次成功就不出。這條以規格的測試段為準。
- **讀取、沒有快取**：維持連續 2 次 `failStreak` 才出橫幅（含逾時）。第一次不出。
- **讀取、有快取**：不出橫幅。
