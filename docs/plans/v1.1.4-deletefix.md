## 3. 刪除從未同步的紀錄：只動本機

仍在 `src/api/index.ts`。`remove` 現在約第 415 行，一律 `write(softDelete)`。改成下面的行為。

### 輔助

在 `recordId` 旁邊加 `opTable(op)`，對應上面的表。加：

```typescript
type LocalStash = { outbox: Queued[]; failed: FailedWrite[] }
```

記憶體裡 `const localUndo = new Map<string, LocalStash>()`，key 是 `` `${table}:${id}` ``。**不要**寫進 IndexedDB。關掉分頁就沒了；佇列的刪除已經 persist，重新開啟不會把紀錄救回來。這是對的。

`let readySettled = false`。現有 `ready` IIFE 的最後、`emit()` 之後、`void flush()` 之前設 `readySettled = true`（heal 做完再設，見第 5 節）。

`takeRelated(table, id)`：

1. 先掃 outbox 和 failed。若 `table === 'Stores'`，把 `upsertItem.record.store === id` 的品項 id、`append.record.store === id` 的 log id 放進一組 id。
2. 相關＝`opTable`＋`recordId` 命中這組 id 的 op（含原本那個店 id）。
3. 從 outbox、failed 濾掉這些 op。從 `failedNotified`（第 4 節）刪掉它們的 qid。
4. 回傳拿掉的 `{ outbox, failed }` 複本。用 `structuredClone`，避免之後改佇列物件連到 stash。

`hasUnsyncedCreate(table, id)`：outbox 或 failed 裡有 **create**，且 `opTable === table` 且 `recordId === id`。店家子項不算。已同步的店即使還有未同步品項，這裡也是 false，`remove` 仍送 `softDelete`，由後端連帶品項。

`dropUnsyncedCreate(table, id)`（同步，在 persist 之前改完記憶體）：

1. 若 `localUndo` 已有這個 key（連點兩次刪除）：直接 `{ queued: false, qid: '' }`，不要再送 `softDelete`。
2. `const taken = takeRelated(table, id)`。
3. `localUndo.set(key, taken)`。
4. `emit()`。
5. persist 走第 4 節的鏈，不要在這裡 `await` 才改記憶體。
6. 回傳 `{ queued: false, qid: '' }`。

### `remove` 必須在 ready 完成後同步丟完，再把 Promise 交回去

`App.tsx` 是 `void api.remove(...)` 然後立刻 `showToast`。使用者可以馬上按「復原」。stash 必須在 `remove()` **回傳之前**就放進 `localUndo`，不能等 microtask。

```javascript
remove(table, id) {
  const run = () => hasUnsyncedCreate(table, id)
    ? dropUnsyncedCreate(table, id)
    : write({ action: 'softDelete', table, id })
  if (readySettled) return Promise.resolve(run())
  return ready.then(run)
}
```

`run()` 裡若走 `dropUnsyncedCreate`，stash 和佇列在 `return` 前改完。`write()` 仍是現在的非同步送出。

沒有 create 的已同步紀錄：行為與現在相同，排 `softDelete`。

### 復原 API

```typescript
undoLocalDrop(table: 'Logs' | 'Items' | 'Stores' | 'Weights', id: string): boolean
```

同步。沒有 stash 就 `false`。有的話：

- `unionByQid`（檔案裡已有）把 stash 的 outbox、failed 放回現在的兩個陣列。不要重複 qid。
- 刪掉這個 stash key。
- 被放回 **failed** 的 qid 加回 `failedNotified`，這樣同一個失敗不會再 toast 一次。
- `emit()`。
- persist 走鏈。
- 若放回的 outbox 長度 > 0，`void flush()`。放回 failed 的不要送。
- 回傳 `true`。

再呼叫一次同一個 id 要回 `false`。

### persist 必須串起來

現在 `persistQueue` 在 `await` 前就 `JSON.stringify`。`remove` 先 stringify 空佇列，使用者按復原又 stringify 救回的佇列，兩個 `kv.set` 誰後完成不一定。後完成的空陣列會蓋掉復原。

改成一條鏈，**在鏈裡才 stringify**（讀到當時的 `outbox`／`failed`／`failedNotified`）：

```javascript
let persistChain: Promise<unknown> = Promise.resolve()
function persistQueue(): Promise<void> {
  const job = persistChain.then(async () => {
    await kv.set('outbox', JSON.stringify(outbox))
    await kv.set('failed', JSON.stringify(failed))
    await kv.set('failedNotified', JSON.stringify([...failedNotified]))
  })
  persistChain = job.then(() => {}, () => {})
  return job
}
```

現有所有 `persistQueue()` 呼叫維持先改記憶體、再呼叫它。不要在呼叫前把 JSON 存進區域變數。

### 公開讀法

加兩個方法，回複本：

- `failed(): FailedWrite[]`，讀活的 `failed` 陣列。`status().failed` 是上次 `emit` 的快照，復原當下可能舊，`dropOrReverse` 不要用它。
- `outbox()` 已有，繼續用。

## 4. failedNotified：同一個失敗只 toast 一次

kv key 字串 `'failedNotified'`。值 `JSON.stringify(string[])`。沒有這個 key 當 `[]`。不要從 localStorage 遷這個 key。

`let failedNotified = new Set<string>()`。在 `ready` 裡、heal **之前**載入：

```javascript
failedNotified = new Set(parseList<string>(await kv.get('failedNotified')))
```

`parseList` 已能處理壞 JSON。

方法：

- `failedNotified(): Promise<string[]>`：`await ready`，回 `[...failedNotified]`。
- `markFailedNotified(qid: string): Promise<void>`：`await ready`，add，然後 `persistQueue()`。

何時刪 qid：

| 動作 | failedNotified |
|---|---|
| `retryFailed` 把某 qid 移回 outbox | **刪掉**這些 qid。使用者按了重試，再失敗要再 toast 一次 |
| `discardFailed`、`dropQueued`、heal、`takeRelated`、`dropUnsyncedCreate` | 刪掉被拿走的 qid |
| `undoLocalDrop` 把 op 放回 failed | **加回**那些 qid（不要再 toast） |

每次 persist 前把 Set 裡「不在 `failed`、也不在任何 stash.failed」的 qid 刪掉，避免陣列無限長。

## 5. ready 時自動修復一次

只在 `ready` IIFE 裡、從 kv 載入 outbox／failed／failedNotified **之後**、**第一次 `emit()` 和 `void flush()` 之前**呼叫一次 `autoHeal()`。不要在 `load()`、`flush()`、`onStatus` 再呼叫。

```javascript
function autoHeal(): number {
  const drop = new Set<string>()
  for (const f of failed) {
    if (f.op.action === 'softDelete' && f.error === 'not_found') drop.add(f.qid)
  }
  const rows = [
    ...outbox.map((op) => ({ qid: op.qid, op })),
    ...failed.map((f) => ({ qid: f.qid, op: f.op })),
  ]
  const groups = new Map<string, { qid: string; op: WriteOp }[]>()
  for (const row of rows) {
    const table = opTable(row.op)
    const id = recordId(row.op)
    if (!table || !id) continue
    const key = table + '\n' + id
    const list = groups.get(key) ?? []
    list.push(row)
    groups.set(key, list)
  }
  for (const list of groups.values()) {
    const hasCreate = list.some((r) => r.op.action === 'append' || r.op.action === 'upsertItem' || r.op.action === 'upsertStore' || r.op.action === 'upsertWeight')
    const hasDel = list.some((r) => r.op.action === 'softDelete')
    if (!hasCreate || !hasDel) continue
    for (const r of list) drop.add(r.qid)
  }
  if (drop.size === 0) return 0
  const before = outbox.length + failed.length
  outbox = outbox.filter((op) => !drop.has(op.qid))
  failed = failed.filter((f) => !drop.has(f.qid))
  for (const q of drop) failedNotified.delete(q)
  return before - outbox.length - failed.length
}
```

規則對齊規格的兩種情況，並把 create 擴到 `upsert*`（否則未同步的品項／店／體重會留下同樣的 not_found 迴圈）：

1. `failed` 裡 `softDelete` 且 `error === 'not_found'`：丟掉這個 op。不管有沒有成對的 create。`outbox` 裡還沒失敗的 softDelete **不要**在這裡丟，讓 `flush` 送；舊後端回 not_found 時由第 2 節當成功。
2. 同一個表＋id 同時有 create（在 outbox 或 failed）和 `softDelete`（在 outbox 或 failed）：這個 id 在兩條清單裡的 op 都丟掉（含夾在中間的 `update`／`restore`）。同一筆被兩條規則命中只算一次。

`n > 0` 時：

```javascript
console.info('food-log auto-heal ' + n)
```

恰一個引數、這一行字、`n` 是被拿掉的 op 數。`n === 0` 不要印。不要 toast。然後 `await persistQueue()`，再 `emit()`，再 `void flush()`。

不要修這些（留在清單裡）：

- 只有 failed `append`、沒有 softDelete（使用者還看得到「沒有存到」）。
- `update` 的 `not_found`。
- `softDelete` 的 `bad_record`／`forbidden`，而且沒有成對的 create。

## 6. `App.tsx`：dropOrReverse 與 toast

### `dropOrReverse`（約第 240 行）

換成這個順序：

```javascript
function dropOrReverse(table: 'Logs' | 'Items' | 'Stores' | 'Weights', id: string, kind: 'append' | 'softDelete' | 'upsertItem' | 'upsertStore' | 'upsertWeight') {
  const api = fl.api
  if (!api) return
  if (api.undoLocalDrop(table, id)) return
  const match = (action: string, recId: string | null, opId?: string) => {
    if (kind === 'append' && action === 'append') return recId === id
    if (kind === 'upsertItem' && action === 'upsertItem') return recId === id
    if (kind === 'upsertStore' && action === 'upsertStore') return recId === id
    if (kind === 'upsertWeight' && action === 'upsertWeight') return recId === id
    if (kind === 'softDelete' && action === 'softDelete') return opId === id
    return false
  }
  const idOf = (op: { action: string; id?: string; record?: { id?: string } }) => ({
    recId: op.record?.id ?? null,
    opId: op.id,
  })
  const q = api.outbox().find((x) => {
    const ids = idOf(x as { action: string; id?: string; record?: { id?: string } })
    return match(x.action, ids.recId, ids.opId)
  })
  if (q) return api.dropQueued(q.qid)
  const f = api.failed().find((row) => {
    const ids = idOf(row.op as { action: string; id?: string; record?: { id?: string } })
    return match(row.op.action, ids.recId, ids.opId)
  })
  if (f) return api.discardFailed(f.qid)
  if (kind === 'append' || kind === 'upsertItem' || kind === 'upsertStore' || kind === 'upsertWeight') return api.remove(table, id)
  return api.restore(table, id)
}
```

「已刪除」的復原會先撞上 stash（第 3 節），把 create 放回原本的清單：原本在 outbox 就回 outbox，原本在 failed 就回 failed。不要再 `api.restore`。

「已記錄」的復原：create 還在 outbox 就 `dropQueued`（與現在相同）。已經掉進 failed 就 `discardFailed`，不要 `remove`（`remove` 會再做一次 stash）。已送出的才 `remove` → 後端 softDelete。

刪除按鈕的呼叫點不要改（約第 538、620、700 行）：仍是 `remove` 然後 toast「已刪除 ＜名＞」，按鈕預設「復原」，`dropOrReverse(..., 'softDelete')`。文案維持「已刪除」，不要改成失敗句。

```javascript
        showToast('收藏沒有存到', act, { actionLabel })
      }
    }
  })()
  return () => { cancel = true }
  // eslint-disable-next-line react-hooks/exhaustive-deps
}, [fl.failed, fl.api])
```

重點：

- 先 `markFailedNotified` 再 `showToast`。同一個 qid 重新開啟 App 不再 toast。
- `await` 回來時若 effect 已清掉（`cancel`），不要 toast。
- 永久錯誤的按鈕是「放棄」，`aria-label` 也是「放棄」（`UndoToast` 用 `actionLabel`）。按下只 `discardFailed`：create 的覆蓋消失，畫面回到伺服器快照；失敗的 softDelete 本來就沒套在畫面上（`applyPending` 跳過 softDelete／restore），列維持看得到。不要送後端、不要第二個 toast。
- 句子裡不要再寫「・重試」。動詞只放在按鈕上。
- `not_found` 的 softDelete 不 toast。heal 應該已經拿掉；這行是保險。
- 非永久錯誤理論上不會在 `failed`。若在，按鈕維持「重試」。
- 不要加 `durationMs`。仍是 3 秒。
- `append` 失敗仍不另外 toast（列上「沒有存到 · 重試」不變）。

店家失敗時關掉 Sheet 的三段 `setStoreUi(null)` 留著，只是改到上面那個分支裡。

行為對照：

| 情況 | 結果 |
|---|---|
| 失敗或還在佇列的 create，使用者按刪除 | 不打後端；列消失；toast「已刪除 …」＋「復原」 |
| 按復原 | create 回到原本的 outbox 或 failed；失敗的那筆不再 toast |
| 已同步的列按刪除 | 仍送 softDelete；失敗且是永久錯誤時 toast「刪除失敗，已還原 …」＋「放棄」，只出現一次 |
| 按放棄 | `discardFailed`，不送後端，沒有第二個 toast |
| 舊後端 softDelete 回 not_found | 當成功，不進 failed，不 toast；成對的未同步 create 一起丟掉 |
| 打開時 kv 裡有 not_found 的 failed softDelete，或 create＋softDelete 成對 | 安靜刪掉；`console.info('food-log auto-heal N')`；不 toast；幽靈列不出現 |
| Kyujin 刪不存在／不是自己的列 | 仍 `forbidden` |
| App 刪不存在或已刪的 id | `{ ok: true }`，不改儲存格、不新增列 |
